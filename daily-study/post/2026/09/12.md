## 주제 1 — 클래스 코드와 헤더 파일, 선언과 정의를 나누는 법

`Calc` 클래스(이전 강의에서 메서드 체이닝 예제로 썼던 바로 그 클래스)를 헤더(`Calc.h`)와 소스(`Calc.cpp`)로 분리하는 법을 배웠다.

- **선언과 정의의 분리**: 헤더에는 멤버 변수와 함수 원형만, 실제 구현은 `.cpp`에 `클래스이름::함수이름` 형태로 작성한다. Visual Studio의 "함수를 .cpp로 이동" 리팩터링 도구를 쓰면 이 과정을 자동화할 수 있다는 것도 실습했다.
- **클래스 안에 정의된 함수는 암묵적으로 inline이다**: 그동안 별생각 없이 클래스 정의 안에 함수 본문을 바로 썼던 것이, 사실은 컴파일러가 자동으로 그 함수를 inline으로 취급하게 만드는 문법적 선택이었다는 것을 처음 명확히 이해했다. 함수를 클래스 밖으로 옮기면 이 암묵적 inline이 사라지므로, 여전히 헤더에 남겨두고 싶다면 `inline`을 명시해야 한다.
- **원본 코드의 실제 링커 오류(가장 인상 깊었던 부분)**: 원본 헤더에 리팩터링 도중 지우지 못한 함수 정의가 그대로 남아 있어서, `.cpp`의 같은 함수 정의와 충돌해 "multiple definition" 링커 오류가 실제로 발생하는 상황을 분석했다. `#pragma once`가 이 문제를 전혀 막아주지 못한다는 것(한 번역 단위 안의 중복만 막아줄 뿐, 서로 다른 번역 단위 사이의 중복은 링커의 몫이라는 것)을 명확히 구분하게 됐다.
- **헤더에 `using namespace std;`를 쓰면 안 되는 이유**: 그 네임스페이스가 그 헤더를 인클루드하는 모든 파일에 전염된다는 것, 그래서 강의가 이를 함수 본문 안으로 옮겨 지역화하는 것을 직접 보여줬다.
- **임시 객체에 대한 메서드 체이닝**: `Calc(10).add(10).sub(1).mult(2).print();`처럼 이름 없는 임시 객체에도 곧바로 체이닝이 가능하다는 것과, 그 임시 객체의 수명이 완전한 표현식(full-expression)이 끝날 때까지 유지된다는 규칙을 새로 배웠다.

## 주제 2 — 클래스와 const, 약속을 컴파일러에게 강제시키기

서로 다른 두 예제로 `const`가 클래스와 만났을 때 벌어지는 일을 배웠다.

- **const 멤버 함수와 this의 타입**: `int getValue() const`에서 `const`는 단순한 표시가 아니라, 함수 안의 `this` 포인터 타입을 `const ClassName* const`로 실제로 바꿔버리는 문법이라는 것을 정확히 이해했다. 이 때문에 `const` 멤버 함수 안에서 멤버를 수정하려는 코드는 컴파일 타임에 즉시 걸러진다.
- **const 여부만으로 가능한, 유일한 예외적 오버로딩(가장 인상 깊었던 부분)**: "반환 타입만으로는 오버로딩할 수 없다"는 절대 규칙을 배웠던 것과 달리, `const string& getValue() const`와 `string& getValue()`는 매개변수가 완전히 같은데도 유효한 오버로딩이 된다. 이유는 눈에 보이지 않는 `this` 매개변수의 타입이 실제로는 다르기 때문이라는 것 — 겉보기 규칙 뒤에 숨은 진짜 메커니즘을 이해하는 것이 왜 중요한지 다시 느꼈다.
- **복사 생성자를 직접 정의해서 관찰하기**: 지금까지 "함수에 객체를 넘기면 복사된다"고 계속 들어왔던 것을, 복사 생성자를 직접 정의해 로그를 찍고 디버거로 주소를 비교하며 실제로 눈으로 확인했다. 값으로 넘긴 매개변수는 원본과 다른 주소를 가진 진짜 사본이고, const 참조로 넘긴 매개변수는 원본과 완전히 같은 주소라는 것을 직접 검증했다.
- **값 vs const 참조 오버로딩의 진짜 모호성**: `print(Something)`과 `print(const Something&)`을 동시에 선언하면 컴파일러가 어느 쪽을 골라야 할지 판단할 수 없어 실제로 "모호한 호출" 오류가 난다는 것을 확인했다 — const 여부로는 오버로딩이 되는데 값/참조만으로는 안 되는 이유를 오버로드 해결 규칙 수준에서 구분할 수 있게 됐다.

## 컴퓨터 구성 요소와의 연결 — 번역 단위, 링커, 그리고 this의 타입

오늘 배운 두 주제를 컴파일 파이프라인 관점에서 이으면 다음과 같다.

```
[8-8: 헤더/소스 분리]
소스 파일(.cpp) 각각이 독립적으로 컴파일 → 오브젝트 파일(.obj)
    │
각 오브젝트 파일은 "따로는" 문제없이 컴파일됨(각자 함수가 1번만 정의된 것처럼 보임)
    │
링커가 여러 .obj를 하나의 실행 파일로 합칠 때
같은 함수의 정의가 두 번 발견되면 → "multiple definition" 오류(ODR 위반)

[8-9: const와 this]
멤버 함수 호출 시 객체의 주소가 this로 암묵적으로 전달됨
    │
그 함수가 const로 선언되어 있으면 this의 타입 자체가
const ClassName* const 로 바뀜
    │
컴파일러는 이 타입 차이만으로 오버로드를 구분하고,
멤버 수정 코드를 컴파일 타임에 차단한다
```

두 경우 모두 **"실수가 실행 중이 아니라, 그보다 훨씬 이른 단계(링크 타임, 컴파일 타임)에서 걸러진다"** 는 것이 핵심이었다. 8-8의 ODR 위반은 "링크 타임"에, 8-9의 const 위반은 "컴파일 타임"에 걸러진다는 점에서, 실수를 잡아내는 시점이 파이프라인의 어느 단계인지도 함께 구분할 수 있게 되었다.

## 셰이더 디자이너·그래픽스 엔지니어 연결점

> [!example] 관점 ① — 헤더 의존성 관리는 대규모 엔진에서 매일 체감하는 문제다
> 8-8에서 배운 "헤더를 고치면 그 헤더를 포함하는 모든 파일이 재컴파일된다"는 사실은, 실제 언리얼/유니티급 엔진 코드베이스에서 반복 빌드-테스트 주기를 늦추는 가장 흔한 원인이다. PImpl 관용구나 전방 선언으로 헤더 의존성을 최소화하는 습관은 셰이더/렌더러 코드를 자주 수정하는 그래픽스 엔지니어에게 실질적인 생산성 차이를 만든다.

> [!example] 관점 ② — const 오버로딩은 엔진 SDK를 읽을 때 실제로 마주친다
> 8-9에서 배운 `getValue() const`/`getValue()` 패턴은 머티리얼·텍스처 리소스 클래스의 API에서 흔히 볼 수 있다. `const` 객체에서는 읽기 전용 버전만 호출되고, 수정 가능한 객체에서는 쓰기 가능한 버전이 호출된다는 원리를 알면, 엔진 SDK 문서 없이도 헤더만 보고 그 함수의 안전성 계약을 즉시 파악할 수 있다.

> [!example] 관점 ③ — 복사 생성자와 pass-by-value는 매 프레임 렌더링 코드의 성능을 좌우한다
> 8-9에서 디버거로 직접 확인한 "값으로 넘기면 복사가 일어난다"는 사실은, `Matrix4x4`나 머티리얼 파라미터 구조체처럼 크기가 큰 타입을 프레임마다 수만 번 함수에 넘기는 렌더링 코드에서 결코 사소하지 않다. `const&`로 바꾸는 것만으로 불필요한 복사 비용을 완전히 제거할 수 있다는 것을 오늘 직접 눈으로 확인했다.

> [!example] 관점 ④ — 임시 객체 체이닝은 셰이더 그래프/빌더 API에서 흔한 패턴이다
> 8-8에서 배운 `Calc(10).add(10)...`처럼 임시 객체에 곧바로 체이닝하는 문법은, 파이프라인 상태 객체(PSO)나 머티리얼 빌더 API를 `Builder().SetShader(vs).SetBlend(blend).Build();`처럼 한 줄로 구성하는 실무 패턴과 원리적으로 동일하다.

## Key Insights

> [!success] Insight 1 — "컴파일은 되는데 링크가 안 되는" 오류는 별개의 사고 범주다
> 8-8의 ODR 위반을 분석하면서, 컴파일 오류와 링크 오류가 서로 다른 단계에서, 서로 다른 이유로 발생한다는 것을 명확히 구분하게 됐다. `#pragma once`가 컴파일 단계의 문제만 해결할 뿐 링크 단계의 문제는 전혀 건드리지 못한다는 것을 알게 된 것이 오늘의 가장 큰 개념적 전환이었다.

> [!success] Insight 2 — "특별한 예외"는 항상 숨겨진 메커니즘을 갖고 있다
> "반환 타입만으로는 오버로딩 불가"라는 규칙에 대한 "const는 예외"라는 사실을 그냥 암기하지 않고, 그 뒤에 숨은 `this` 포인터 타입 차이까지 파고드니 왜 그것이 예외가 되는지 완전히 납득할 수 있었다. 앞으로 "이건 예외다"라는 규칙을 마주칠 때마다, 그 뒤에 숨은 진짜 메커니즘을 찾아보는 습관을 들여야겠다.

> [!success] Insight 3 — 디버거로 "눈에 보이지 않는 호출"을 실제로 확인하는 습관
> 복사 생성자 호출, this 포인터 전달처럼 소스 코드에 명시적으로 드러나지 않는 동작들을, 디버거로 주소를 비교하며 직접 확인하는 방법이 이번 주 내내 반복해서 등장했다. 이제 "이게 진짜 일어나는 일인가"를 의심할 때 디버거를 켜는 것이 자연스러운 습관이 되어가고 있다.

## Key Takeaways

| # | 개념 | 핵심 요약 | 실무·연구 연결 |
|---|---|---|---|
| 1 | 선언과 정의 분리 | 헤더에는 원형만, `.cpp`에 `클래스::함수` 형태로 구현 | 대규모 코드베이스의 인터페이스/구현 분리 |
| 2 | 암묵적 inline | 클래스 안에 정의된 함수는 자동으로 inline 취급 | 헤더 밖으로 옮기면 명시적 inline 필요 |
| 3 | One Definition Rule | 비-inline 함수는 프로그램 전체에서 정의가 하나여야 함 | "multiple definition" 링커 오류의 근본 원인 |
| 4 | 헤더의 using namespace 금지 | 헤더의 using 선언은 포함하는 모든 파일에 전염됨 | 이름 충돌 버그의 예방 |
| 5 | 임시 객체 체이닝 | 이름 없는 객체도 즉시 메서드 체이닝 가능, 수명은 완전한 표현식까지 | 빌더 패턴 API 설계 |
| 6 | const 멤버 함수 | this의 타입을 `const T* const`로 바꿔 멤버 수정을 차단 | 컴파일 타임 실수 방지 |
| 7 | const 오버로딩 | this의 상수성 차이로 성립하는 유일한 예외적 오버로딩 | 엔진 SDK의 getter 설계 패턴 |
| 8 | 복사 생성자 | 값으로 전달 시 자동 호출, 디버거로 주소 비교해 실증 가능 | 대형 구조체 pass-by-value의 숨은 비용 |
| 9 | const 참조 전달 | 복사 없이 원본을 그대로 참조, 포인터 크기만큼만 전달 | 렌더링 핫패스에서의 필수 최적화 |
| 10 | 값 vs const 참조 오버로딩 | 우열을 가릴 기준이 없어 모호한 호출 오류 발생 | 오버로딩 설계 시 반드시 피해야 할 조합 |
