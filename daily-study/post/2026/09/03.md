## 주제 1 — GigaThread 전역 스케줄러, GPU의 작업 분배 총괄자

드로우 콜이 들어오면 GPU는 정점·픽셀 수백만 개를 병렬로 처리해야 한다. 이 작업을 물리적 연산 장치인 **SM(Streaming Multiprocessor)** 들에게 나눠주는 최상위 하드웨어가 **GigaThread 전역 스케줄러**(NVIDIA GPU 기준)다.

```
CPU (드로우 콜/커널 호출)
        │
GigaThread 전역 스케줄러 — GPU 전체에 단 1개
  · 그리드를 "스레드 블록" 단위로 분배
        │
   ┌────┴────┬────────┐
  SM #0     SM #1  ...  SM #N
   │
Warp 스케줄러 (SM당 2~4개)
  · 블록을 32개 스레드 묶음(Warp)으로 관리
  · 물리 코어(SP)에 실제 실행 할당
```

핵심은 **2단계 스케줄링 구조**다.

- **전역 스케줄러**: "블록"을 SM들에게 분배하는 거시적(Macro) 역할 — GPU에 1개.
- **워프 스케줄러**: SM 내부에서 "워프(32스레드)"를 물리 코어에 스왑해주는 미시적(Micro) 역할 — SM마다 여러 개.

이 구분을 모르고 "GPU 스케줄러"를 뭉뚱그려 설명하면 로우레벨 이해도가 얕다는 인상을 준다는 것을 오늘 명확히 정리했다. 또한 스레드 블록의 총 개수가 SM 개수보다 적으면 일부 SM이 유휴 상태로 남는다는 것, 컴퓨트 셰이더의 스레드 그룹 크기 설계가 곧 이 전역 스케줄러가 나눠줄 블록의 크기를 결정한다는 것도 함께 정리했다.

> 이 주제의 전체 정리(로우레벨 동작 단계별 분해, 부하 분산 실무, 트러블슈팅 사례까지)는 [[../../../300. 💠 Artifact Archive/03_CS/02_개념/GigaThread 전역 스케줄러_GigaThread Global Scheduler|GigaThread 전역 스케줄러]] 노트에 완결되어 있다.

## 주제 2 — 디스크립터와 디스크립터 힙, GPU가 리소스를 찾는 방법

VRAM은 그 자체로 평평한 바이트 덩어리일 뿐이다. GPU에게 "이 주소를 읽어라"라고만 하면, 그 데이터가 2D 텍스처인지 3D 텍스처인지, 포맷이 무엇인지 전혀 알 수 없다. 이 문제를 해결하는 메타데이터 구조체가 **디스크립터(Descriptor)**다.

- 과거(DX11): 드라이버가 매 드로우 콜마다 디스크립터를 검증·바인딩 → 심각한 **드라이버 오버헤드**.
- 현대(DX12/Vulkan): 모든 디스크립터를 VRAM 위 **디스크립터 힙(Descriptor Heap)**에 미리 정렬해두고, CPU는 가벼운 인덱스(오프셋)만 전달.

$$\text{address} = \text{base\_address} + \text{offset} \times \text{descriptor\_size}$$

이 수식 하나로 GPU가 힙 안의 원하는 리소스를 즉시 찾아낸다는 것이 오늘 배운 핵심 원리다. 이 방식이 극단화되면, 모든 리소스가 이미 힙에 상주한 상태에서 인덱스만 바꿔가며 참조하는 **바인딩리스(Bindless) 렌더링**이 가능해지고, 결과적으로 API 오버헤드가 사라지고 [[../../../300. 💠 Artifact Archive/03_CS/02_개념/PCIe 대역폭_PCI Express Bandwidth|PCIe 버스]] 트래픽이 극적으로 줄어든다. 용도별로 SRV(읽기 전용 텍스처)·UAV(읽ss기/쓰기 버퍼)·CBV(상수 버퍼)·RTV(렌더 타깃)·DSV(깊이 버퍼) 다섯 종류의 디스크립터가 존재하며, 셰이더가 이 디스크립터 테이블을 어떤 순서로 받을지는 **루트 시그니처(Root Signature)** 가 정의한다는 것도 함께 정리했다.

> 이 주제의 전체 정리(도서관 비유, API 진화 과정, 힙/풀 메모리 구조, 바인딩리스 심화)는 [[../../../300. 💠 Artifact Archive/02_컴퓨터 그래픽스/02_개념/디스크립터_Descriptor|디스크립터_Descriptor]] 노트에 완결되어 있다.

## 주제 3 — LCD 모니터의 물리적 구조, 신호가 빛이 되는 과정

주연테크 모니터 실제 분해 영상을 보며, GPU가 계산한 프레임버퍼가 케이블을 떠난 뒤 실제 "빛"이 되기까지의 물리적 경로를 처음부터 끝까지 추적했다.

```
GPU 프레임버퍼 → HDMI/DP 케이블 → AD보드(스케일러) → LVDS 케이블 → T-CON → 액정 전압
```

- **AD보드(스케일러)**: 컴퓨터의 메인보드·CPU에 해당하는 부품. 입력 신호를 패널 네이티브 해상도로 스케일링.
- **LVDS 케이블**: 차동 신호(+/−)로 노이즈에 강하게 데이터를 전송.
- **T-CON(타이밍 컨트롤러)**: 각 픽셀 전극에 정확한 타이밍으로 전압을 나눠 공급.

패널 자체는 **스스로 빛을 내지 못하는 광 밸브**다. 뒤에서 균일한 빛을 공급하는 **BLU(Back Light Unit)**가 반드시 필요하며, 오늘 실물 실험 사진으로 그 6겹 구조를 전부 확인했다 — ① 패널 백프레임(열 변형 방지) → ② LED 바(점광원) → ③ 반사시트(빛샘 회수) → ④ 도광판(점광원→면광원 확산) → ⑤ 확산시트(균일화) → ⑥ 프리즘 시트(재집광, 휘도 상승). 이 모든 층의 목적은 단 하나, **"점발광을 면발광으로 고르게 퍼뜨리는 것"**이었다.

마지막으로 빛은 **뒤쪽 편광판 → 액정(전압에 따라 편광 회전) → 컬러필터(RGB 부여) → 앞쪽 편광판**을 순서대로 통과하며 최종 색과 밝기로 변조된다. 액정은 발광체가 아니라 "빛의 투과량을 조절하는 밸브"라는 것이 오늘 가장 인상 깊었던 개념이었다.

> 이 주제의 전체 정리(28장의 실물 분해 사진과 각 단계 설명, TN/VA/IPS 비교, OLED와의 차이)는 [[../../../300. 💠 Artifact Archive/03_CS/02_개념/LCD 모니터 속 구조와 각 필름들이 하는 일|LCD 모니터 속 구조와 각 필름들이 하는 일]] 노트에 완결되어 있다.

## 주제 4 — 휘도와 측광학, 빛이 밝기로 인식되는 물리량

셰이더에서 흔히 쓰는 그레이스케일 공식 $Y = 0.2126R + 0.7152G + 0.0722B$는 임의의 숫자가 아니라, 인간의 망막이 파장별로 느끼는 민감도를 나타내는 **CIE 측광 곡선(V(λ))**을 방송 표준 원색 좌표로 수치화한 결과라는 것을 오늘 물리학적으로 정리했다.

- **방사도학(Radiometry)**: 인간의 눈을 배제한 순수 물리 에너지($W/(m^2\cdot sr)$, [[../../../300. 💠 Artifact Archive/06_물리학, 광학/02_개념/방사휘도_Radiance|방사휘도]]).
- **측광학(Photometry)**: 방사도학 수치에 인간의 시각 민감도를 곱한 인지적 밝기($\text{cd/m}^2$, 니트).

휘도는 이 둘을 잇는 다리이며, 초록 채널이 압도적으로 높은 가중치를 갖는 이유(555nm 부근 최대 민감도)가 여기서 나온다. 또한 SDR(80~100nit)과 HDR(수십만 nit) 사이의 압도적인 동적 범위 차이, 그리고 그 범위를 디스플레이에 맞게 압축하는 톤 매핑의 존재 이유도 함께 정리했다.

> 이 주제의 전체 정리(CIE 측광 곡선, 단위 체계, SDR/HDR 실측 표, 톤 매핑과의 연결)는 [[../../../300. 💠 Artifact Archive/06_물리학, 광학/02_개념/휘도_Luminance|휘도_Luminance]] 노트에 완결되어 있다.

## 컴퓨터 구성 요소와의 연결 — 픽셀 하나의 전체 여정

오늘 배운 네 주제를 하나의 파이프라인으로 이으면 다음과 같다.

```
① GigaThread 전역 스케줄러
   드로우 콜/디스패치 → 스레드 블록을 SM에 분배
        │
② 디스크립터 힙
   각 스레드가 셰이더 안에서 텍스처·버퍼를
   인덱스 하나로 VRAM에서 직접 참조
        │
   [셰이더 연산 완료 → 프레임버퍼 완성]
        │
③ 디스플레이 신호 경로
   HDMI/DP → AD보드(스케일러) → LVDS → T-CON
        │
   T-CON이 각 픽셀 전극에 전압 인가
        │
④ LCD 패널의 광학 변조
   BLU(면발광) → 편광판 → 액정(전압에 따라 회전)
   → 컬러필터 → 편광판 → 최종 색·밝기
        │
⑤ 인간의 시각 인지
   그 밝기는 임의의 값이 아니라 CIE 측광 곡선이
   반영된 "휘도"라는 물리량으로 엄밀히 정의됨
```

GPU 내부의 스케줄링 하드웨어부터 시작해, 리소스를 참조하는 메모리 구조, 신호를 실제 빛으로 바꾸는 디스플레이 하드웨어, 그리고 그 빛을 밝기로 해석하는 인간의 생물학적 수용체까지 — 오늘 하루 공부한 네 주제가 렌더링 파이프라인의 "시작"과 "끝"을 정확히 채워준다는 것을 확인했다.

## 셰이더 디자이너·그래픽스 엔지니어 연결점

> [!example] 관점 ① — 디스크립터 구조를 알면 머티리얼 파라미터 설계가 달라진다
> 상용 엔진에서는 텍스처 노드 하나를 추가하는 것이 내부적으로 SRV 디스크립터 하나를 힙에 등록하는 것과 같다는 것을 알게 되면, 머티리얼에 텍스처 파라미터를 무분별하게 늘리는 것이 단순히 "샘플링 비용" 문제가 아니라 디스크립터 힙 용량과 셰이더 컴파일 시간에도 영향을 준다는 것을 근거 있게 설명할 수 있다.

> [!example] 관점 ② — GPU 스케줄링 구조는 컴퓨트 셰이더 설계의 실전 기준이 된다
> GigaThread 전역 스케줄러가 스레드 블록 단위로 SM에 작업을 분배한다는 것을 알면, 컴퓨트 셰이더의 스레드 그룹 크기를 SM 개수 대비 너무 작지도 크지도 않게 설계해야 하는 이유를 물리적 근거로 설명할 수 있다. 이는 파티클 시뮬레이션이나 GPU 기반 컬링 시스템을 직접 구현할 때 바로 쓰이는 지식이다.

> [!example] 관점 ③ — LCD의 물리 구조를 알면 "왜 이 색이 이렇게 보이는가"에 답할 수 있다
> 편광판이 원리상 빛의 상당량을 흡수한다는 것, 패널 종류(TN/VA/IPS)마다 시야각과 명암비가 다르다는 것을 알면, 같은 셰이더 결과물이 모니터마다 다르게 보이는 이유를 아트 디렉션과 QA 단계에서 하드웨어적 근거로 설명할 수 있다. 포트폴리오에서 "왜 이 모니터 기준으로 색을 잡았는가"를 답할 수 있는 근거가 된다.

> [!example] 관점 ④ — 휘도 공식은 물리학에서 파생된 셰이더 코드다
> `dot(color, float3(0.2126, 0.7152, 0.0722))` 한 줄이 CIE 측광 곡선이라는 인간 시각의 생물학적 데이터를 그대로 코드화한 것이라는 사실은, 그래픽스 프로그래밍이 순수 수학이 아니라 물리학·생물학과 맞닿아 있다는 것을 보여주는 가장 좋은 예시다. 이 근거를 설명할 수 있다는 것 자체가 석사 수준의 이해도를 증명하는 포인트다.

## Key Insights

> [!success] Insight 1 — 모든 최적화 구조는 "미리 준비하고, 나중엔 가볍게 참조한다"는 동일한 패턴을 따른다
> GigaThread의 블록 사전 분배, 디스크립터 힙의 사전 등록, BLU의 사전 배치된 광학 필름 — 형태는 다르지만 전부 "무거운 작업을 초기에 몰아서 처리하고, 런타임에는 가벼운 인덱스/신호만 주고받는다"는 동일한 엔지니어링 철학을 공유한다.

> [!success] Insight 2 — "발광"과 "변조"는 다른 개념이다
> LCD 패널은 스스로 빛을 내지 않고 BLU가 만든 빛을 "변조"할 뿐이라는 것이, OLED가 스스로 "발광"하는 것과 근본적으로 다르다는 것을 물리적으로 이해했다. 이 구분이 두 디스플레이 기술의 명암비·전력 효율·두께 차이를 전부 설명한다.

> [!success] Insight 3 — 셰이더의 상수 하나에도 물리학적 근거가 있다
> 그레이스케일 가중치 0.7152라는 숫자가 임의로 정해진 것이 아니라 인간 망막의 555nm 민감도 곡선에서 유도되었다는 것을 알게 되면서, 셰이더 코드의 "매직 넘버"들을 더 이상 암기가 아니라 근거로 다룰 수 있게 되었다.
