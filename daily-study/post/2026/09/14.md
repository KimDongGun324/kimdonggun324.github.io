## 주제 1 — 벡터 핵심 정리, 내적과 외적의 기하학적 의미

레이 트레이싱 엔진 제작에 필요한 벡터 수학의 이론적 기초를 다시 세웠다.

- **내적의 진짜 의미**: `A·B = |A||B|cos(θ)`라는 공식을 암기하는 것을 넘어, "A를 B 방향으로 투영한 길이 × |B|"라는 기하학적 해석을 정리했다. 내적이 0이면 두 벡터가 수직이라는 성질 하나가 조명 계산(N·L), 컬링 판정, 수직 검사 전부의 기초라는 것을 다시 확인했다.
- **외적과 좌표계 손잡이**: 외적의 계산 공식 자체(성분별 수식)는 좌표계의 손잡이(왼손/오른손)와 무관한 순수 대수 연산이며, 달라지는 것은 "그 결과가 실제로 어느 물리적 방향을 가리키는가"에 대한 해석뿐이라는 것을 정밀하게 정리했다. DirectX(왼손)와 OpenGL(오른손) 사이에서 법선이 뒤집히는 버그의 근본 원인이 바로 이 지점이다.
- **부동소수점 오차 처리**: 수직 판정처럼 실수 연산 결과를 0과 비교할 때는 정확히 0이 아니라 작은 epsilon 범위 안에 있는지로 판정해야 한다는 원칙을 실무 예제(`abs(dotProduct) < 0.0001f`)로 재확인했다.

## 주제 2 — GLM, 이론을 실제 코드로 옮길 때 생기는 함정들

GLM은 GLSL과 거의 동일한 문법(`vec3`, `dot()`, `normalize()`, `cross()`)을 C++에서 그대로 쓸 수 있게 해주는 헤더 온리 라이브러리다. 오늘 가장 크게 배운 것은 이론과 실제 코드 사이의 간극에서 생기는 함정들이었다.

- **`vec3 * vec3`는 내적도 외적도 아니다**: GLM(그리고 GLSL/HLSL)에서 벡터끼리 `*` 연산자를 쓰면 성분별 곱(Hadamard product)이 나온다. 색상 곱셈에서는 우연히 의도한 대로 작동하기 때문에 더 헷갈리기 쉽다는 것을 배웠다.
- **GPU 상수 버퍼의 정렬(alignment) 문제**: GLSL의 std140 레이아웃에서 `vec3`는 16바이트로 패딩되는데, C++ `glm::vec3`는 12바이트라서 그대로 매핑하면 셰이더가 엉뚱한 값을 읽는다 — 컴파일 오류 없이 조용히 발생하는 종류의 버그라는 점이 특히 위험하다.
- **정규화 함정**: 0벡터를 정규화하면 NaN이 나오고, 이 NaN은 이후의 모든 연산(내적, 외적, 행렬 곱)에 전염된다. 길이나 `dot(v, v)`로 먼저 확인하는 방어 코드가 필수라는 것을 다시 정리했다.
- **"GLM은 느리다"는 절반만 맞는 말**: `GLM_FORCE_SSE2` 같은 매크로로 SIMD를 활성화할 수 있다는 것, DirectXMath의 진짜 강점은 연산 속도보다 D3D 상수 버퍼 레이아웃과의 통합에 있다는 것을 정확히 구분했다.

## 주제 3 — 원 그리기, 판정 로직이 곧 SDF였다

2D 화면에 원을 그리는 아주 단순한 CPU 예제였지만, 그 안에 실무 그래픽스의 핵심 아이디어가 압축되어 있었다.

- **점-원 판정은 곧 SDF**: `f(P) = |P - C| - r`이 음수면 원 안, 0이면 경계, 양수면 원 밖이라는 것 — 이것이 바로 부호 있는 거리 함수(SDF)의 가장 단순한 형태라는 것을 처음으로 명확히 언어화했다. Inigo Quilez의 SDF 함수 모음이나 레이 마칭 셰이더가 결국 이 원리의 확장이라는 것을 깨달았다.
- **`sqrt()`를 피하는 이유**: 화면의 모든 픽셀(수십만 개)에 대해 매 프레임 실행되는 판정에서, 부등식 양변을 제곱해도 순서가 보존된다는 성질(`|P-C| ≤ r ⟺ |P-C|² ≤ r²`)을 이용해 `sqrt()` 호출 자체를 제거하는 최적화를 배웠다. 다만 이 트릭은 안티앨리어싱처럼 실제 거리가 필요한 연산에는 쓸 수 없다는 한계도 함께 정리했다.
- **CPU 래스터화 대 GPU 셰이더**: 동일한 판정 로직을 CPU 이중 for문으로 처리하는 것과 GPU 프래그먼트 셰이더 한 줄로 병렬 처리하는 것을 직접 대응시켜 봤다. `D3D11_MAP_WRITE_DISCARD`로 텍스처를 갱신하는 이유(버퍼 리네이밍)도 함께 정리했다.
- **이미지 좌표계 vs 수학 좌표계**: 이미지가 메모리에 저장되는 순서(왼쪽 위부터) 때문에 Y축이 아래로 증가한다는 실용적인 이유를 다시 확인했다.

## 컴퓨터 구성 요소와의 연결 — CPU 래스터화부터 SIMD까지

오늘 배운 네 주제를 하드웨어 관점에서 이으면 다음과 같다.

```
[벡터 연산 하나] x, y, z 세 성분에 대한 동시 연산
    │
CPU의 SIMD 레지스터(SSE/AVX)가 vec4(128비트)를 한 번의 명령어로 처리
    │
[원 그리기: CPU 래스터화]
width × height번의 독립적인 IsInside() 판정을 CPU 코어가 순차 처리
    │
[동일한 로직을 셰이더로 이식하면]
GPU의 수천 개 코어가 모든 픽셀을 동시에(SIMT 구조) 병렬 처리
    │
CPU에서 계산한 결과는 Map/Unmap + memcpy로 GPU 메모리에 업로드해야 하며,
이 전송 자체가 PCIe 대역폭 비용을 발생시킨다
```

**"당혹스러울 만큼 병렬적인(embarrassingly parallel)" 문제** — 각 픽셀의 판정이 다른 픽셀과 완전히 독립적이라는 성질 — 이 바로 GPU가 CPU보다 압도적으로 빠른 근본 이유라는 것을 오늘 다시 한번 명확히 정리했다.

## 셰이더 디자이너·그래픽스 엔지니어 연결점

> [!example] 관점 ① — SDF는 셰이더 아트의 언어다
> 오늘 정리한 "원 판정은 곧 SDF"라는 통찰은 폰트 렌더링(SDF 폰트), 벡터 아이콘, 레이 마칭 기반 볼류메트릭 렌더링까지 이어지는 셰이더 디자이너의 핵심 도구다. `float sdf = length(p - center) - radius;` 한 줄에서 시작해 여러 SDF를 `min`/`max`로 조합하면 텍스처 없이 순수 수식만으로 복잡한 벡터 그래픽을 그릴 수 있다.

> [!example] 관점 ② — GPU 상수 버퍼 정렬 문제는 그래픽스 엔지니어가 반드시 아는 지식이다
> `vec3`가 std140에서 16바이트로 패딩된다는 사실을 모르면, C++ 구조체와 셰이더 유니폼 블록 사이에 컴파일 오류 없이 조용히 어긋나는 버그를 만들게 된다. 오늘 이 문제를 명확히 이해한 것은 실무에서 겪을 뻔한 디버깅 시간을 미리 아낀 것과 같다.

> [!example] 관점 ③ — 좌표계 손잡이는 멀티 API 엔진의 숙명이다
> DirectX(왼손)와 OpenGL/Vulkan(오른손) 사이를 오가며 동일한 메시·조명 코드를 재사용하려면 좌표계 변환을 어디서 어떻게 적용할지 명확한 정책이 있어야 한다. 오늘 정리한 "외적 공식은 손잡이와 무관하고 해석만 달라진다"는 이해가 이 정책을 설계하는 데 직접적인 근거가 된다.

> [!example] 관점 ④ — CPU 프로토타입을 GPU로 옮기는 감각
> 원 그리기 예제의 CPU 루프를 HLSL 프래그먼트 셰이더로 직접 변환해 본 경험은, "이 계산을 GPU로 옮기면 어떻게 되는가"를 항상 염두에 두고 코드를 짜는 습관으로 이어진다. 이는 셰이더 프로토타이핑을 C++로 먼저 검증한 뒤 셰이더로 이식하는 실무 워크플로우와 정확히 일치한다.

## Key Insights

> [!success] Insight 1 — "겉보기 규칙"과 "실제 동작"을 구분하는 습관
> `vec3 * vec3`가 내적처럼 보이지만 실제로는 성분별 곱이라는 것, 외적 공식은 손잡이와 무관하지만 결과 해석은 다르다는 것처럼, 오늘은 유독 "이름/직관과 실제 동작이 다른" 지점들을 많이 만났다. 앞으로 새로운 API나 연산자를 만날 때마다 "이게 정말 내가 생각하는 그 연산이 맞는가"를 한 번 더 검증하는 습관을 들여야겠다.

> [!success] Insight 2 — 단순한 예제가 복잡한 기술의 축소판일 수 있다
> 원 그리기라는 초급 예제가 사실은 SDF 렌더링, 레이 마칭이라는 고급 셰이더 기술의 가장 단순한 형태였다는 것을 깨달은 것이 오늘의 가장 큰 전환점이었다. 앞으로 "쉬운 예제"를 볼 때도 "이게 어떤 고급 기술의 축소판일 수 있는가"를 생각해보는 습관을 들이고 싶다.

> [!success] Insight 3 — 컴파일 오류 없이 조용히 발생하는 버그가 가장 위험하다
> GPU 상수 버퍼 정렬 문제, 좌표계 손잡이 불일치 모두 컴파일은 멀쩡히 되지만 결과가 조용히 틀어지는 종류의 버그다. 이런 버그는 사전 지식 없이는 발견 자체가 어렵기 때문에, 오늘처럼 이론을 미리 정확히 정리해 두는 것이 실전 디버깅 시간을 아끼는 가장 확실한 방법이라는 것을 다시 느꼈다.

| 8 | CPU 래스터화 vs GPU 병렬 | 동일 로직도 GPU에서는 완전 병렬로 처리됨 | 프로토타입을 셰이더로 이식하는 실무 워크플로우 |
| 9 | 0벡터 정규화 함정 | 정규화 전 길이/`dot(v,v)` 확인 필수, 아니면 NaN 전염 | 렌더링 크래시의 흔한 원인 진단 |
