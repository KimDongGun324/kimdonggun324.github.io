## 주소에 의한 전달 기본 원리 — 세 가지 출력의 의미

```cpp
void foo(int *ptr)
{
    cout << *ptr << " " << ptr << " " << &ptr << endl;
    //     ▲역참조값  ▲저장된주소  ▲포인터 자신의 주소
}
```

함수가 `int *ptr` 을 매개변수로 받으면 호출 시 전달한 주소값이 ptr에 **복사**된다. 세 가지 출력은 완전히 다른 것을 가리킨다.

| 표현식 | 의미 | 이미지에서 확인된 값 |
|--------|------|----------------------|
| `*ptr` | **역참조** — ptr이 가리키는 메모리의 값 | 5 |
| `ptr` | 포인터에 담긴 **주소값** (value의 주소와 동일) | 001EFE94 |
| `&ptr` | 포인터 변수 자체가 존재하는 주소 (foo 스택) | 001EFDB4 |

> **역참조(dereference)**: `*ptr` 은 ptr에 저장된 주소로 이동해 그 위치의 값을 읽는 연산이다. 배열의 `arr[i]` 도 역참조 — 내부적으로 `*(arr + i)` 와 동일하다.

## 이미지로 증명 — 포인터 전달은 내부적으로 값 복사

**이미지 1 — 기본 실행 결과:**

```
main:          5   010FFBAC
               (value 값)  (value 주소)

foo(ptr):      5   010FFBAC   010FFACC
               (*ptr)  (ptr 값)  (&ptr in foo)

foo(&value):   5   010FFBAC   010FFACC
               (완전히 동일)
```

**이미지 2 — main의 &ptr 추가 출력으로 결정적 증명:**

```
main:  5    001EFE94   ← value 값, &value
main:  001EFE88        ← main에서 ptr 자체의 주소
foo:   5    001EFE94   001EFDB4   ← *ptr, ptr, &ptr in foo
foo:   5    001EFE94   001EFDB4   (foo(&value)도 동일)
```

결정적 비교:

| 변수 | 주소 | 해석 |
|------|------|------|
| main의 `ptr` | 001EFE88 | main 스택에 있는 포인터 변수 |
| foo 내부의 `ptr` | 001EFDB4 | foo 스택에 새로 생긴 포인터 변수 |
| 두 ptr이 담은 값 | 001EFE94 (동일) | value의 주소 — 복사된 값 |

> [!important] 핵심 증명
> 001EFE88 과 001EFDB4 는 **다르다** → 포인터 변수 자체가 복사되어 foo 스택에 새로 생겼다. 반면 두 ptr이 담은 값(001EFE94)은 같다 → 같은 value를 가리킨다. **포인터 전달은 "주소라는 값을 담은 변수"를 복사하는 값에 의한 전달이다.** 어제 참조 전달에서 `&y` 와 `&x` 가 동일했던 것과 완전히 대조된다.

## 세 가지 호출 방법과 rvalue 불가 이유

```cpp
int value = 5;
int *ptr = &value;

foo(ptr);       // ptr에 저장된 주소값 복사 전달
foo(&value);    // value의 주소를 직접 계산해 전달 → 결과 동일
// foo(5);      // 컴파일 에러: 5는 rvalue, 주소가 없음
```

| 호출 방식 | 전달되는 것 | 컴파일 | 이유 |
|-----------|-------------|--------|------|
| `foo(ptr)` | ptr에 저장된 주소 복사 | O | ptr은 lvalue |
| `foo(&value)` | value의 주소 직접 계산 | O | &value도 주소값 |
| `foo(5)` | — | X 에러 | 5는 rvalue, 주소 없음 |

`foo(ptr)` 과 `foo(&value)` 는 함수 내부에서 완전히 동일하게 동작한다. 이미지에서 두 줄의 출력이 완벽히 같음이 이를 증명한다.

> [!info] const 붙이면 rvalue도 가능할까?
> 참조 전달에서는 `const int &x` 로 선언하면 `foo(5)` 가 가능했다. 그러나 포인터는 `const int *ptr` 로 선언해도 `foo(5)` 는 불가능하다. 리터럴 5의 주소를 얻을 방법이 없기 때문이다.

## typedef로 포인터 가독성 향상

```cpp
typedef int* pint;   // pint 는 int* 의 타입 별칭

void foo(pint ptr)   // void foo(int *ptr) 과 완전히 동일
{
    cout << *ptr << " " << ptr << " " << &ptr << endl;
}
```

`typedef` 를 사용하면 `pint ptr` 처럼 쓸 수 있어 외관상 일반 값 전달처럼 보인다. 교수님이 의도적으로 이 형태를 보여주신 이유 — **포인터 전달이 결국 값 복사임을 시각적으로 강조하기 위해서**다.

> [!warning] typedef 포인터 함정
> `typedef int* pint;` 정의 후 `pint a, b;` 를 쓰면 a, b 모두 `int*` 가 된다. 그러나 `typedef` 없이 `int *a, b;` 를 쓰면 a만 포인터, b는 `int` 다. 모던 C++에서는 `using pint = int*;` 를 선호한다.

## 포인터를 이용한 다중 출력 — 참조 전달과 비교

```cpp
// 포인터 방식 (주소에 의한 전달)
void getSinCos_ptr(double degrees, double *sin_out, double *cos_out)
{
    *sin_out = std::sin(degrees * 3.14159 / 180.0);   // 역참조 후 대입
    *cos_out = std::cos(degrees * 3.14159 / 180.0);
}

// 참조 방식 (참조에 의한 전달, 7.3)
void getSinCos_ref(double degrees, double &sin_out, double &cos_out)
{
    sin_out = std::sin(degrees * 3.14159 / 180.0);    // 역참조 연산자 없음
    cos_out = std::cos(degrees * 3.14159 / 180.0);
}
```

**호출부 차이가 핵심이다:**

```cpp
double sin = 0.0, cos = 0.0;

getSinCos_ptr(30.0, &sin, &cos);   // 포인터: & 반드시 붙여야 함
getSinCos_ref(30.0, sin, cos);     // 참조:   변수 이름만 넘김
```

이미지 3에서 `sin` 과 `cos` 출력이 각각 1과 2로 나타남 → 함수 내에서 `*sin_out` 와 `*cos_out` 로 역참조해 값을 쓰면 호출자의 변수가 수정됨이 확인된다.

| 비교 기준 | 참조 전달 | 포인터 전달 |
|-----------|-----------|-------------|
| 매개변수 선언 | `double &out` | `double *out` |
| 함수 내 수정 | `out = 1.0` | `*out = 1.0` |
| 호출부 | `func(x)` | `func(&x)` |
| null 가능 여부 | 불가 — 항상 유효 | 가능 (`nullptr`) |
| 코드 간결성 | 높음 | 낮음 (역참조 `*` 필요) |
| 교수님 선호 | ✓ 더 선호 | △ C 스타일 레거시 |

> 교수님: "실용적인 면에서는 참조를 쓰는 게 더 좋다. 포인터는 C 스타일 코드에서 아주 많이 쓰였던 방식이다."

## const 포인터의 세 가지 형태

`const` 를 어디에 붙이느냐에 따라 의미가 완전히 달라진다. **오른쪽에서 왼쪽으로 읽는 법**을 익히면 쉽다.

**형태 1: `const int *ptr` — 가리키는 값이 const (비권장: pointer to const)**

```cpp
const int *ptr = &value;

// *ptr = 10;  // 에러: 가리키는 값 수정 불가
ptr = &other;  // OK: 포인터 주소는 변경 가능
```

**형태 2: `int * const ptr` — 포인터 자체가 const (const pointer)**

```cpp
int * const ptr = &value;

*ptr = 10;     // OK: 가리키는 값 수정 가능
// ptr = &other; // 에러: 포인터 주소 변경 불가
```

**형태 3: `const int * const ptr` — 둘 다 const (const pointer to const)**

```cpp
const int * const ptr = &value;

// *ptr = 10;    // 에러
// ptr = &other; // 에러
```

**한 눈에 비교:**

| 선언 | 역참조 값 수정 | 포인터 주소 변경 |
|------|----------------|------------------|
| `int *ptr` | O | O |
| `const int *ptr` | X | O |
| `int * const ptr` | O | X |
| `const int * const ptr` | X | X |

> [!info] 왜 이중 const 를 쓰는가?
> 교수님 말씀: "오픈 소스를 보시면 이렇게 const 가 두 개 있는 구조를 보실 수 있다." 포인터가 함수 내에서 실수로 다른 주소를 가리키거나 값을 수정하는 두 가지 버그를 모두 컴파일 타임에 방지한다. 그러나 포인터 자체(ptr)는 결국 값 복사이므로 ptr 주소를 막는 두 번째 const 는 외부에 영향이 없다 — 주로 코드 내의 의도를 명확히 하는 용도다.

> [!info] 강의 4번 코드블록의 에러 설명
> 강의 코드의 `foo (int i = 0; ...)` 는 오타로, 실제로는 `for` 루프다. 또한 `const int * const ptr` 로 선언 후 `*ptr = &x;` 를 시도하는 부분은 ① const 포인터라 역참조 값 수정 불가, ② `&x` 는 `int*` 이고 `*ptr` 은 `const int` 이므로 타입 불일치 — 두 가지 이유로 컴파일 에러가 발생하는 의도적인 에러 시연 코드다.

## 배열과 포인터 전달 — array decay

```cpp
void printArray(const int *arr, int length)
{
    for (int i = 0; i < length; i++)
        cout << arr[i] << ' ';   // arr[i]는 *(arr + i) 와 동일
}

int main()
{
    int arr[] = { 1, 2, 3, 4, 5 };
    printArray(arr, 5);   // 배열 이름이 첫 원소 포인터로 자동 붕괴
}
```

**배열 붕괴(array decay)**: 배열 이름 `arr` 은 `&arr[0]` 과 동일한 포인터로 자동 변환된다. 이 변환에서 배열의 크기 정보가 사라지므로 **`length` 를 별도로 전달해야 하는 불편함**이 생긴다.

```cpp
sizeof(arr)              // main 안: 20바이트 (5 * 4)
sizeof(arr in function)  // 함수 안: 8바이트 (포인터 크기만 남음)
```

> **왜 배열 전달에 포인터가 효율적인가?**
> 원소 1000개짜리 배열을 값으로 복사하면 4000바이트. 포인터 하나만 복사하면 8바이트. 교수님: "어레이를 보낼 때 주소 하나가 복사되는 것은 수많은 데이터를 모두 복사하는 것보다 훨씬 효율이 좋다."

## 참조 vs 포인터 — 종합 비교

| 기준 | 참조 (`int &ref`) | 포인터 (`int *ptr`) |
|------|-------------------|---------------------|
| 메모리 | 원본과 동일 주소 공유 | 주소값을 복사한 별도 변수 |
| 역참조 연산자 | 불필요 | `*ptr` 필수 |
| null 허용 | 불가 — 항상 유효 | 가능 (`nullptr`) |
| 재할당 | 불가 (바인딩 고정) | 가능 (다른 변수 가리킬 수 있음) |
| 호출부 | `func(x)` | `func(&x)` |
| C 호환성 | C에 없음 | C와 완전 호환 |
| 배열 전달 | `const vector<int>&` | `int*, int len` |
| 교수님 선호 | ✓ (모던 C++) | 레거시·API 호환 용도 |

## 컴퓨터 구성 요소와의 연결 — 스택·캐시·역참조

**스택 메모리 레이아웃 — 포인터 복사 과정:**

```
  높은 주소
  ┌──────────────────────────────────────┐
  │  main 스택 프레임                     │
  │    int value  @ 001EFE94 : 5        │  ← 원본 변수
  │    int *ptr   @ 001EFE88 : 001EFE94 │  ← ptr은 value의 주소 저장
  ├──────────────────────────────────────┤
  │  foo 스택 프레임                      │
  │    int *ptr   @ 001EFDB4 : 001EFE94 │  ← 주소값이 복사된 새 ptr
  └──────────────────────────────────────┘
  낮은 주소
```

참조 전달과의 차이:

```
참조 전달:   main [x @ 00AFFCC0] ↔ addOne [&y → 00AFFCC0]  (같은 주소)
포인터 전달: main [ptr @ 001EFE88] → foo [ptr @ 001EFDB4]  (다른 주소, 같은 값)
```

**역참조와 CPU 메모리 접근:**
역참조 `*ptr` 는 CPU가 ptr에 저장된 주소(001EFE94)로 이동해 그 위치의 4바이트를 읽는다. 이 주소가 L1/L2 캐시에 있으면 수 사이클이지만 캐시 미스가 나면 수백 사이클을 소비한다.

| 하드웨어 | 역할 |
|----------|------|
| **RAM (스택)** | 포인터 변수와 원본 변수가 각 프레임에 존재 |
| **메모리 버스** | 역참조 `*ptr` 시 실제 메모리 접근 수행 |
| **L1/L2 캐시** | 역참조 대상 주소의 캐시 히트/미스 결정 |
| **레지스터** | 포인터값(8바이트)이 레지스터로 전달되는 경우 있음 |

# AI 생성 참고용

## 셰이더 디자이너·그래픽스 엔지니어 연결점

> [!example] 관점 ① — OpenGL C API는 포인터 전달의 집합체다
> OpenGL은 C 언어로 설계된 API이기 때문에 모든 다중 출력 패턴이 포인터로 구현된다. `glGenBuffers(1, &vbo)` 는 오늘 배운 `getSinCos_ptr(deg, &sin, &cos)` 와 동일한 구조다 — 내부에서 생성된 값을 `&vbo` 주소에 저장한다. `glBufferData(GL_ARRAY_BUFFER, size, vertices, GL_STATIC_DRAW)` 에서 `vertices` 는 배열 이름이 포인터로 붕괴되어 전달된다. `glGetIntegerv(GL_MAX_TEXTURE_SIZE, &maxSize)` 는 `const int *` 를 통해 드라이버가 값을 내려준다. 그래픽스 엔지니어가 OpenGL 코드를 처음 읽을 때 `&` 와 `*` 가 난무해 보이지만, 오늘 배운 원리 하나로 모두 해석된다.

> [!example] 관점 ② — Vulkan / DirectX 12 에서의 이중 const 패턴
> Vulkan API 함수는 `const VkAllocationCallbacks *pAllocator`, `const VkInstanceCreateInfo *pCreateInfo` 처럼 const 포인터를 입력으로 받고, `VkInstance *pInstance` 처럼 비const 포인터를 출력으로 사용한다. 오늘 배운 `const int *ptr` (읽기 전용), `int *ptr` (쓰기 가능)의 구분이 그대로 적용된다. DirectX 12의 `ID3D12Device::CreateCommittedResource(..., ID3D12Resource **ppvResource)` 는 이중 포인터를 통해 생성된 자원 핸들을 돌려준다 — 이것은 포인터 참조(`int *&ptr`) 대신 C API 스타일로 이중 포인터를 쓴 것이다.

> [!example] 관점 ③ — 버텍스 버퍼 데이터와 배열 포인터 전달
> GPU에 버텍스 데이터를 업로드할 때 `glBufferData` 또는 `memcpy` 로 배열을 전달한다. 이때 배열 이름이 포인터로 붕괴되어 첫 번째 원소의 주소만 전달되며, 크기 정보는 별도의 `sizeof(vertices)` 또는 `vertexCount * sizeof(Vertex)` 로 계산해 넘겨야 한다. 오늘 배운 `printArray(const int *arr, int length)` 패턴이 렌더링 파이프라인에서 버텍스 버퍼 유틸리티 함수로 그대로 사용된다. C 스타일 배열 전달의 한계(크기 정보 소실)를 이해해야 버퍼 오버런 버그를 예방할 수 있다.

> [!example] 관점 ④ — CPU-GPU 메모리 공간 분리와 포인터의 한계
> CPU에서 `int *ptr` 이 특정 RAM 주소를 가리킬 때, 그 주소는 GPU VRAM의 어떤 위치와도 직접 대응되지 않는다. CPU 포인터를 GPU 셰이더에 그대로 넘기는 것은 불가능하며, 반드시 버퍼 오브젝트를 통해 데이터를 복사해야 한다. `glMapBuffer` 또는 Vulkan의 `vkMapMemory` 가 CPU 주소 공간에 GPU 메모리를 매핑하는 과정이고, 이 매핑된 포인터(`void *data`)를 통해 데이터를 쓴 뒤 언매핑한다. 포인터가 "메모리 주소라는 값을 담은 변수"임을 이해해야, CPU-GPU 경계에서 포인터가 왜 직접 통하지 않는지를 직관적으로 파악할 수 있다.

## Key Insights

> [!success] Insight 1 — `&ptr` 주소가 다르다는 사실이 모든 것을 설명한다
> 참조 전달에서는 함수 내부의 `&y` 와 main의 `&x` 가 동일했다. 포인터 전달에서는 foo 내부의 `&ptr` (001EFDB4)과 main의 `&ptr` (001EFE88)이 다르다. 이 단 하나의 관찰이 "포인터 전달은 주소값을 복사하는 값에 의한 전달"임을 완전히 증명한다. 메모리 주소를 직접 출력해 검증하는 C++ 특유의 방법론이 다시 한번 강력함을 보여준다.

> [!success] Insight 2 — 포인터 전달이 참조처럼 "원본을 바꾸는 것"처럼 보이는 이유
> `*ptr = 99;` 를 함수 내에서 실행하면 호출자의 변수가 바뀐다. 마치 참조 전달처럼 보이지만 원리는 완전히 다르다. 포인터는 주소값을 복사해서 받고, 그 복사된 주소를 타고 원본 메모리에 도달해 값을 바꾼다. 참조는 처음부터 같은 메모리를 두 이름으로 부르는 것이다. 포인터를 함수 내에서 다른 주소로 변경해도(`ptr = &other`) 호출자의 포인터는 변하지 않는 것이 이 차이를 입증한다.

> [!success] Insight 3 — const 포인터의 위치가 보호 대상을 결정한다
> `const` 가 `*` 앞에 오면 역참조 값을 보호, `*` 뒤에 오면 포인터 주소를 보호한다. 오른쪽에서 왼쪽으로 읽는 법(`const int * const ptr` → "ptr은 const 포인터인데, const int를 가리킨다")을 익히면 어떤 복잡한 포인터 선언도 해석할 수 있다. Vulkan/OpenGL API 함수 시그니처를 읽을 때 이 규칙이 반드시 필요하다.

> [!success] Insight 4 — 배열은 포인터가 아니지만 포인터로 붕괴된다
> `int arr[5]` 와 `int *p` 는 전혀 다른 타입이다. `sizeof(arr)` 는 20바이트지만 함수에 전달되는 순간 `int*` 로 붕괴되어 8바이트가 된다. 이 붕괴가 C 스타일 배열 API에서 항상 `length` 를 별도로 받아야 하는 이유다. 모던 C++에서 `std::vector<int>&` 나 `std::span<int>` 를 쓰는 것이 이 문제를 근본적으로 해결한다.
