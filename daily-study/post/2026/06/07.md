## 참조 전달의 핵심 — 복사 없이 같은 주소

참조(Reference)는 이미 존재하는 변수에 대한 **또 다른 이름(alias)** 이다.

```cpp
int x = 5;
int &y = x;   // y는 x의 별칭 — 동일한 메모리 주소 공유
```

- `int &y` 에서 `&` 는 주소 연산자가 아니라 **참조 선언자**다.
- y는 별도 메모리 공간을 갖지 않는다 → **복사 비용 0**
- 한 번 바인딩된 참조는 다른 변수를 가리키도록 변경할 수 없다 → 포인터와 근본적 차이

| 구분 | 매개변수 선언 | 별도 메모리 생성 | 호출자 변수 영향 | 복사 비용 |
|------|---------------|------------------|------------------|-----------|
| **값 전달** | `int y` | O (새 스택 공간) | 없음 | 있음 |
| **참조 전달** | `int &y` | X (주소 공유) | 있음 | 없음 |

## addOne 분석 — 주소 일치로 참조 증명

```cpp
void addOne(int &y)
{
    cout << y << " " << &y << endl;   // 함수 내부: y의 주소 출력
    y = y + 1;                         // x를 직접 수정
}

int main()
{
    int x = 5;
    cout << x << " " << &x << endl;   // [1] 5  00AFFCC0
    addOne(x);
    cout << x << " " << &x << endl;   // [3] 6  00AFFCC0
}
```

**실행 결과 (이미지 기준):**

```
[1] main 호출 전:       5   00AFFCC0   ← x의 주소
[2] addOne 내부:        5   00AFFCC0   ← y의 주소 (x와 동일!)
[3] main 호출 후:       6   00AFFCC0   ← x 값이 6으로 변경됨
```

> [!info] 핵심: 주소가 같다는 것의 의미
> main의 `&x`(00AFFCC0)와 addOne 내부의 `&y`(00AFFCC0)가 **완전히 같다**. 이는 새로운 변수가 생성되지 않았음을 의미한다. y는 x의 별칭으로, 같은 메모리 셀 하나를 두 이름으로 접근하고 있다. 값 전달에서는 주소가 달랐던 것과 정반대다.

**값 전달과의 결정적 차이:**

```
값 전달:    main [x @ 00AFFCC0] → doSomething [y @ 00AFF800]  (주소 다름)
참조 전달:  main [x @ 00AFFCC0] ↔ addOne [y ↗ 00AFFCC0]      (주소 동일)
```

## getSinCos — 다중 출력 참조 패턴

C++ 함수는 return 값이 하나뿐이다. 여러 값을 동시에 돌려줘야 할 때 **비const 참조 매개변수를 출력 채널**로 활용하는 패턴이 전통적이다.

```cpp
void getSinCos(const double &degrees, double &sin_out, double &cos_out)
//              ▲ 입력(읽기 전용)     ▲ 출력          ▲ 출력
{
    static const double degToRad = 3.141592653589793 / 180.0;
    const double radians = degrees * degToRad;
    sin_out = std::sin(radians);
    cos_out = std::cos(radians);
}
```

**매개변수 역할 분류:**

| 매개변수 | 한정자 | 역할 | 특징 |
|----------|--------|------|------|
| `const double &degrees` | `const &` | **입력** | 함수 내 수정 불가, 복사 없음 |
| `double &sin_out` | `&` | **출력** | 함수 내 수정 → 호출자 반영 |
| `double &cos_out` | `&` | **출력** | 위와 동일 |

**관례 (교수님 강조):**
- **앞쪽** 매개변수: `const 타입&` → 입력
- **뒤쪽** 매개변수: `타입&` → 출력
- const가 있으면 "입력", 없고 `&`만 있으면 "출력"이라고 직관적으로 읽을 수 있다

> [!info] 왜 참조로 입력도 받는가?
> `const double &degrees` 는 double(8바이트) 복사 없이 원본을 읽는다. `const`를 붙여 수정을 막으면서 복사 비용을 줄이는 것이다. 대형 구조체일수록 이 이점이 커진다.

## static const 최적화 원리

```cpp
static const double degToRad = 3.141592653589793 / 180.0;
```

- **`static`**: 함수를 100번 호출해도 **최초 1회만 초기화**된다. 이후 호출에서는 이미 계산된 값을 재사용하므로 나눗셈 연산이 반복되지 않는다.
- **`const`**: 초기화 이후 값 변경을 **컴파일 타임에 차단**한다. 실수로 값을 덮어쓰는 버그를 방지한다.

**중간 계산 결과에도 const 적극 활용:**
```cpp
const double radians = degrees * degToRad;   // 이후 코드에서 radians 수정 불가
```

> [!success] 성능 팁
> 컴파일러는 `static const` 값을 **컴파일 타임 상수 접기(constant folding)** 로 처리할 수 있다. 런타임 나눗셈 연산 자체가 사라지고 미리 계산된 상수가 코드에 박혀버린다. 렌더링 파이프라인처럼 매 프레임 수천 번 호출되는 함수에서 누적 성능 이점이 생긴다.

## const 참조와 rvalue 리터럴 바인딩

```cpp
void foo(const int &x)
{
    cout << x << endl;
}

int main()
{
    foo(6);   // 리터럴 6을 const int& 로 전달 → 정상 컴파일
}
```

리터럴 `6` 은 메모리 주소가 없는 **rvalue**다.

| 매개변수 선언 | `foo(6)` 가능? | 이유 |
|---------------|----------------|------|
| `int &x` | X — 컴파일 에러 | 비const 참조는 lvalue만 수용 |
| `const int &x` | O — 정상 동작 | 컴파일러가 임시 변수를 생성해 6을 저장, 그 주소를 참조에 바인딩 |
| `int x` | O — 정상 동작 | 값 전달은 rvalue도 수용 |

**해결 방법 두 가지 (교수님 설명):**
1. `void foo(int x)` — 참조를 없애고 값 전달로 변경
2. `void foo(const int &x)` — `const` 추가 → rvalue 수용

## 포인터에 대한 참조 — typedef 활용

```cpp
typedef int* pint;         // pint는 int*의 타입 별칭

void foo(pint &ptr)        // void foo(int *&ptr) 와 완전히 동일
{
    cout << ptr << " " << &ptr << endl;
}

int main()
{
    int x = 5;
    pint ptr = &x;
    cout << ptr << " " << &ptr << endl;
    foo(ptr);   // 포인터 변수 자체가 참조로 넘어감
}
```

**`int *&ptr` 읽는 법 — 오른쪽에서 왼쪽으로:**

```
int  *  &  ptr
 ▲   ▲   ▲
 |   |   └─ "ptr은..."
 |   └───── "참조(&)인데,"
 └───────── "int 포인터(int*)에 대한 참조다"
```

**이미지 실행 결과:**
- main의 `&ptr` 와 foo 내부의 `&ptr` 가 **동일한 주소** 출력
- 포인터 변수 자체가 복사 없이 함수로 넘어갔음을 증명

**typedef의 가독성 효과:**

| 선언 방식 | 코드 | 직관성 |
|-----------|------|--------|
| 원본 형태 | `void foo(int *&ptr)` | 낮음 — `*`와 `&`가 뒤섞여 혼란 |
| typedef 활용 | `void foo(pint &ptr)` | 높음 — "pint 타입 변수를 참조로" |

> [!info] 포인터 참조의 실무 활용
> 이중 포인터(`int **`) 대신 `int *&` 를 쓰면 가독성이 높아진다. 특히 함수 내에서 **포인터가 가리키는 주소 자체를 변경**해야 할 때 (예: 동적 할당 후 핸들 반환) 이 패턴을 사용한다. typedef나 `using` 별칭으로 복잡한 포인터 타입을 단순화하는 습관이 실무에서 매우 유효하다.

## 배열을 참조로 전달하는 방법

**C 스타일 — 비권장:**
```cpp
void printElement(int (&arr)[4])   // 크기 4인 배열만 수용, 유연성 없음
```
괄호 없이 `int &arr[4]` 로 쓰면 "참조의 배열"로 해석되어 컴파일 에러 발생.

**모던 스타일 — 권장:**
```cpp
void printElement(const vector<int> &arr)   // 크기 무관, 복사 없음
```

| 방식 | 크기 유연성 | 복사 비용 | 교수님 실무 선택 |
|------|-------------|-----------|------------------|
| `int (&arr)[4]` | X — 크기 고정 | 없음 | 실제 코드에서 한 번도 사용 안 함 |
| `const vector<int>&` | O | 없음 | 항상 이 방식 |
| `const std::array<int,N>&` | △ — 크기 고정이나 타입 안전 | 없음 | 대안으로 사용 가능 |

> 교수님이 직접 강조하신 포인트: "실제 코드에서 C 스타일 배열 참조로 구현한 적이 한 번도 없다. STL 컨테이너를 참조로 넘기는 게 훨씬 편하다."

## 값 전달 vs 참조 전달 비교

| 기준 | 값 전달 (`int y`) | 참조 전달 (`int &y`) |
|------|-------------------|----------------------|
| **메모리** | 새 스택 공간 + 복사 | 포인터(8바이트)만 전달 |
| **주소** | 호출자와 다름 | 호출자와 동일 |
| **호출자 영향** | 없음 | 있음 |
| **안전성** | 높음 (부작용 없음) | 낮음 (의도적 수정 필요) |
| **대형 객체 성능** | 복사 비용 큼 | 복사 없음 |
| **rvalue 전달** | 가능 | 불가 (const& 는 가능) |
| **GLSL 대응** | `in` (기본값) | `out` / `inout` |

**교수님 선호 코딩 스타일 (모던 C++):**
```
입력 매개변수  →  const 타입&
출력 매개변수  →  타입&         (뒤에 배치)
```

## 컴퓨터 구성 요소와의 연결 — 스택·캐시·레지스터

**스택 프레임과 참조 전달의 물리적 동작:**

```
값 전달:
  ┌──────────────────────────┐
  │ main 프레임              │
  │   int x @ 00AFFCC0 : 5  │
  ├──────────────────────────┤
  │ addOne 프레임            │
  │   int y @ 00AFF800 : 5  │  ← 새 공간에 복사
  └──────────────────────────┘

참조 전달:
  ┌──────────────────────────┐
  │ main 프레임              │
  │   int x @ 00AFFCC0 : 5  │
  ├──────────────────────────┤
  │ addOne 프레임            │
  │   int &y → 00AFFCC0     │  ← 포인터만 전달, 복사 없음
  └──────────────────────────┘
```

**CPU 캐시 관점:**

| 상황 | 캐시 동작 | 결과 |
|------|-----------|------|
| 소형(int, float) 값 전달 | 레지스터 이동 1회 — 사실상 무료 | 성능 차이 없음 |
| 대형 구조체 값 전달 | 수십~수백 바이트 스택 복사 → 캐시 라인 오염 | 캐시 미스 유발 |
| `const 구조체&` 참조 전달 | 포인터(8바이트)만 전달 → 원본 캐시 라인 유지 | 캐시 히트율 보존 |

**레지스터와 컴파일러 최적화:**
- 컴파일러 최적화(-O2 이상)에서 참조 포인터는 레지스터에 올라가 메모리 접근을 최소화
- `static const` 상수는 상수 접기(constant folding)로 런타임 연산이 제거됨
- 작은 함수는 인라인화되어 참조 전달 오버헤드 자체가 0이 됨

# AI 생성 참고용 자료

## 셰이더 디자이너·그래픽스 엔지니어 연결점

> [!example] 관점 ① — GLSL `in` / `out` / `inout` 은 C++ 세 전달 방식의 직접 대응
> GLSL과 HLSL의 매개변수 한정자는 C++ 참조 패턴과 일대일로 대응한다. `in vec3 position`은 C++의 `const glm::vec3 &position`처럼 읽기 전용이고, `out vec4 fragColor`는 `glm::vec4 &fragColor`처럼 출력 전용이며, `inout float3 value`는 입출력 모두 가능하다. 오늘 배운 getSinCos의 `const double &degrees` (입력) / `double &sin_out` (출력) 구분이 GLSL 셰이더 함수 설계의 기본 문법과 동일하다. CPU 사이드 렌더링 코드와 셰이더 코드를 동시에 읽고 쓰는 그래픽스 엔지니어에게 이 대응 관계는 필수 지식이다.

> [!example] 관점 ② — 행렬과 대형 구조체는 반드시 const 참조로 전달하라
> 렌더링 루프에서 Model-View-Projection 행렬(`glm::mat4`, 64바이트)을 값으로 전달하면 draw call마다 64바이트 복사가 발생한다. 씬 그래프를 순회하며 수천 번 함수를 호출하는 루프라면 이 복사 비용이 프레임 타임에 직접적인 영향을 미친다. `const glm::mat4 &mvp`로 선언하면 포인터(8바이트)만 전달되어 복사 비용이 0에 수렴하고, 원본 행렬의 캐시 라인도 그대로 유지된다. 그래픽스 프로그래머의 첫 번째 성능 습관이다.

> [!example] 관점 ③ — GPU 자원 핸들(GLuint, ID3D12Resource)과 다중 출력 참조 패턴
> OpenGL에서 VBO와 VAO를 생성하는 초기화 함수는 항상 `void createBuffers(GLuint &outVBO, GLuint &outVAO)` 형태를 갖는다. 이것은 오늘 배운 getSinCos의 `double &sin_out` 패턴과 구조적으로 완전히 동일하다. C++ 함수가 return으로 하나의 값만 돌려줄 수 있기 때문에, GPU 자원 핸들처럼 여러 값을 생성해 돌려줄 때 참조 출력 매개변수가 필수다. DirectX 12와 Vulkan에서는 `ID3D12Resource **ppResource`(이중 포인터)나 `ComPtr<ID3D12Resource> &resource`(스마트 포인터 참조)로 발전하는데, 이 모두가 오늘 배운 `int *&ptr` 개념의 확장이다.

> [!example] 관점 ④ — RVO와 Constant Buffer 준비 최적화
> CPU에서 GPU로 보낼 Constant Buffer(DirectX) / Uniform Buffer(OpenGL·Vulkan) 데이터를 구조체로 준비할 때 `PerFrameConstants buildFrameData(const Camera &cam)` 같은 함수를 자주 작성한다. 컴파일러 RVO(Return Value Optimization)가 적용되면 이 구조체가 최종 목적지 버퍼에 직접 생성되어 `memcpy` 없이 GPU로 전달된다. 모던 C++(C++17 이후)에서 RVO가 보장되는 케이스를 이해하면 구식의 출력 참조 매개변수 패턴을 제거하고 코드 가독성을 유지하면서도 동일한 성능을 얻을 수 있다.

## Key Insights

> [!success] Insight 1 — 주소가 같다는 것이 참조 전달의 모든 것을 설명한다
> 값 전달에서 `&x` ≠ `&y` 였던 것이, 참조 전달에서는 `&x` 와 `&y` 가 00AFFCC0 으로 완전히 동일해진다. 이 하나의 사실이 "복사 없음", "호출자 변수 직접 수정", "복사 비용 0" 을 모두 설명한다. 주소 출력으로 메모리 레벨의 사실을 눈으로 확인하는 것이 C++ 을 공부하는 가장 강력한 방법이다.

> [!success] Insight 2 — const & 는 입력, & 만 있으면 출력 — 이 관례가 코드를 읽는 속도를 바꾼다
> getSinCos 의 매개변수 목록을 보면 `const&` 는 함수가 이 값을 읽기만 하고, `&` 만 있으면 함수가 이 변수를 통해 결과를 돌려줄 것임을 즉시 파악할 수 있다. 이 관례를 알면 오픈 소스 렌더링 코드를 읽을 때 함수 시그니처만으로 데이터 흐름을 파악할 수 있다. OpenGL, Vulkan, DirectX API 함수들이 모두 이 관례를 따른다.

> [!success] Insight 3 — typedef 로 복잡한 타입을 단순화하면 `int *&ptr` 도 읽을 수 있다
> `int *&ptr` 은 처음 보면 혼란스럽지만, `typedef int* pint` 를 이용해 `pint &ptr` 로 쓰면 "pint 타입의 참조"로 자연스럽게 읽힌다. 이 기법은 이중·삼중 포인터, 함수 포인터, GPU 핸들 등 복잡한 타입을 다룰 때 실수를 크게 줄여준다. 현대 C++ 에서는 `typedef` 대신 `using pint = int*;` 를 권장한다.

> [!success] Insight 4 — 모던 C++ 은 출력 참조 매개변수 패턴을 구조적 바인딩으로 대체한다
> `getSinCos(degrees, sin_out, cos_out)` 처럼 여러 출력 매개변수를 나열하는 전통적 방식은 C++17 이후 `auto [s, c] = getSinCos(degrees)` 처럼 구조적 바인딩과 tuple/pair 반환으로 대체되고 있다. 그러나 OpenGL·DirectX API 등 레거시 코드에는 여전히 참조 출력 패턴이 광범위하게 사용되므로, 두 방식 모두 읽고 쓸 수 있어야 한다.
